# Requirements

> 이 문서는 `TeamProject_Req1.pdf`의 1차 요구사항을 기준으로 정리한 초안입니다.
> PDF에 직접 명시된 내용과 팀에서 추가로 결정해야 하는 내용을 구분합니다.
> 팀 논의 및 교수님 설명에 따라 수정될 수 있습니다.

## 1. 프로젝트 기본 방향

- Java 21 이상 환경에서 실행 가능한 테트리스 게임을 개발한다.
- 대상 운영체제는 Windows 11 또는 macOS 26 이상 중 하나를 선택할 수 있다.
- 팀 추가 목표는 Windows 11과 macOS 26 이상을 모두 지원하는 것이다. 지원할 CPU 아키텍처는 팀 장비 확인 후 결정한다.
- 1차 요구사항은 기본적인 테트리스 게임 구현을 목표로 한다.
- 이후 요구사항이 추가될 예정이므로 확장을 고려하여 설계한다.
- 3차에 걸친 요구사항 추가에 맞춰 매 반복 주기마다 실행·검증 가능한 버전을 유지한다.
- 텍스트 기반 게임이라는 조건을 충족하는 UI 표현 방식을 정한다. Swing 사용 범위가 모호하면 e-class에 확인한다.

## 2. 시작 메뉴

시작 메뉴에는 다음 항목이 있어야 한다.

- 게임 이름
- 게임 시작
- 설정
- 스코어보드
- 게임 종료

추가 요구사항:

- 키보드로 메뉴 사이를 이동할 수 있어야 한다.
- Enter(Return) 키로 메뉴를 선택할 수 있어야 한다.
- 다른 키를 사용하는 경우 화면에 사용 가능한 키를 표시해야 한다.
- 이후 메뉴가 추가될 수 있도록 설계해야 한다.

## 3. 기본 테트리스 게임

### Board

- 보드는 20줄 × 10칸이다.
- 블럭을 쌓아 한 행을 모두 채우면 해당 행이 삭제된다.

### Tetromino

- 참조 코드에 제시된 7종의 블럭을 구현한다.
- 다음 블럭은 동일한 확률로 무작위 결정되어야 한다.
- 각 블럭은 서로 다른 색상을 가져야 한다.
- 유사한 모양이나 좌우가 바뀐 블럭은 쉽게 구분될 수 있도록 대비되는 색상이나 무늬를 사용해야 한다.

### 화면 표시

게임 화면에는 최소한 다음 내용이 포함되어야 한다.

- Board
- 다음에 생성될 블럭
- 현재 점수

점수는 게임 진행에 따라 실시간으로 갱신되어야 한다.

다음 블럭 미리보기의 표시 개수는 팀에서 결정하며, 새 블럭 생성 시 표시를 갱신한다.

## 4. 게임 조작

- 현재 블럭은 조작이 없어도 초기에는 1초에 1칸씩 아래로 떨어져야 한다.
- 일정 수 이상의 블럭이 생성되거나 줄이 삭제되면 낙하 속도가 증가해야 한다.
- 키보드로 다음 동작을 수행할 수 있어야 한다.
  - 왼쪽으로 1칸 이동
  - 오른쪽으로 1칸 이동
  - 아래로 1칸 이동
  - 시계방향 90도 회전
  - 한 번에 끝까지 아래로 떨어뜨리기(Hard Drop)
- 반복된 키 입력이 무시되지 않고 즉시 정확하게 반응해야 한다.
- 게임 진행 중 일시정지/재개 기능이 있어야 한다.
- OS의 Alt+F4 등에 의존하지 않고 게임 내부에서 종료할 방법이 있어야 한다.
- 이동·회전 시 보드 경계와 기존 블럭을 통과하지 않으며, 일시정지 중 자동 낙하가 중단되어야 한다.
- 반복 입력, 일시정지·재개 및 게임 내부 종료 동작을 두 운영체제에서 검증한다.

## 5. 점수

PDF에 직접 명시된 기본 규칙:

- 블럭이 1칸 아래로 떨어질 때마다 1점을 획득한다.
- 자동 하강과 수동 하강 모두 동일하게 점수를 획득한다.
- 낙하 속도가 초기 속도보다 빨라진 경우 추가 점수를 획득한다.
- PDF에 직접 제시되지 않은 점수 가산/감산 방식도 최소 1개 이상 추가해야 한다.

### 팀에서 결정할 사항

- 속도가 빨라졌을 때 추가 점수를 몇 점 줄지
- 별도로 추가할 점수 규칙
- Hard Drop에 별도 점수를 줄지 여부
- Line Clear 점수를 별도로 둘지 여부
- Hard Drop 이동 칸에 기본 낙하 점수를 적용하는 구체적인 방식(모호하면 교수님께 확인)
- 가속 상태의 추가 점수와 복수 행 삭제 점수 계산 방식

## 6. 색맹 모드

- 설정에서 색맹 모드를 켜고 끌 수 있어야 한다.
- 적녹 색각이상 및 청황 색각이상에서도 블럭 구분이 쉬워야 한다.
- PDF에 제시된 접근성 관련 참고자료를 확인하여 디자인에 반영한다.

### 팀에서 검토할 사항

- 색상 조합
- 외곽선
- 패턴 또는 문자 표시 사용 여부
- 명도 차이
- 흑백 환경에서도 블럭 구분이 가능한지
- 유사하거나 좌우가 반전된 블럭도 구별되는지 색각 시뮬레이션·패턴 등으로 확인할 방법

## 7. 설정

설정 화면에서 다음 기능을 제공해야 한다.

- 게임 화면 크기 조절
  - 미리 정의된 크기를 최소 3가지 이상 제공
- 게임 조작 키 설정
- 스코어보드 기록 초기화
- 색맹 모드 On/Off
- 모든 설정을 기본값으로 복구
- 변경된 설정 저장
- 다음 프로그램 실행 시 저장된 설정 복원

그 밖의 필요한 설정은 추가할 수 있다.

- 화면 크기를 변경해도 보드의 논리적 크기(20×10)는 유지한다.
- 설정 파일은 설치 폴더가 아닌 사용자별 저장 경로에 두고, 파일이 없거나 읽을 수 없을 때의 동작을 정한다.
- 설정 초기화와 스코어보드 기록 초기화는 구분한다.

## 8. 게임 종료

- 더 이상 블럭을 쌓을 수 없으면 게임이 종료되어야 한다.
- 게임 종료 시 스코어보드를 표시한다.
- 현재 점수가 스코어보드에 기록될 조건을 만족하면 이름 입력 화면을 표시한다.
- 이름 입력 후 스코어보드를 갱신하고 방금 입력한 이름과 점수를 강조하여 표시한다.
- 스코어보드 처리가 끝난 뒤 시작 메뉴로 돌아가거나 프로그램을 종료할 수 있어야 한다.

## 9. 스코어보드

- 역대 점수 순위를 표시한다.
- 이름과 점수 등을 높은 점수 순으로 정렬한다.
- 최소 상위 10개 이상의 기록을 포함한다.
- 프로그램을 종료해도 기록이 유지되어야 한다.
- 설정 화면에서 초기화하기 전까지 기록이 유지되어야 한다.
- 동일 점수 순위, 기록 진입 기준, 이름 입력 제한은 팀에서 정하고 테스트한다.

## 10. 실행 환경 및 성능

- Java 21 이상
- Windows 11 또는 macOS 26 이상 중 하나
- 팀 추가 목표: Windows 11 및 macOS 26 이상 각각에서 실행·입력·저장 기능 검증
- 1.2GHz 이상 프로세서
- 1GB RAM
- 500MB 이상의 여유 디스크 공간
- 위 사양에서 게임 플레이에 문제가 없을 정도의 성능을 제공해야 한다.

## 11. 프로젝트 관리

프로젝트 진행 중 발생하는 다음 산출물을 적절하게 관리한다.

- 코드
- 관련 문서
- 논의사항
- 이슈와 해결상황
- 팀원별 업무분담

코드는 VCS를 이용하여 관리한다.

중간 및 최종 결과물에서는 위 관리 내역을 제시할 수 있어야 한다.

- 요구사항에 식별자를 부여하고 관련 Issue, PR 및 테스트를 연결한다.
- 각 반복 개발 주기에서 우선순위·담당자·완료 기준·결과를 기록한다.
- 요구사항이 추가·변경되면 영향받는 기능과 회귀 테스트를 함께 검토한다.

## 12. 테스트

- 충분한 단위 테스트를 작성한다.
- 직접 작성한 코드의 Line Coverage를 50~70% 이상 확보한다.
- 비기능적 요구사항의 충족 여부를 검증하는 테스트를 최소 1개 이상 작성한다.
- 테스트 코드도 적절히 관리한다.
- 변경사항이 발생할 때 테스트를 손쉽게 반복 실행할 수 있는 체계를 갖춘다.
- Unit Test Framework 및 Code Coverage 관리 도구를 사용한다.
- Coverage 측정 대상과 목표값을 팀에서 확정하고, 기능별 정상·경계·실패 사례를 검증한다.
- 자동 테스트 결과와 별개로 최소 사양 및 OS별 실제 패키지 실행을 확인한다.

## 13. 실행 및 배포

- 배포용 패키지를 손쉽게 생성할 수 있는 체계를 갖춘다.
- 배포용 패키지에는 아이콘이 포함된 실행파일이 있어야 한다.
- 사용자가 실행파일을 더블클릭하는 등의 일반적인 OS 동작으로 실행할 수 있어야 한다.
- 사용자가 `java -cp ...` 같은 명령어를 직접 입력하도록 해서는 안 된다.
- Java 21 이상이 설치되어 있고 경로가 설정되어 있다고 가정해도 된다.
- 또는 JRE를 패키지에 포함하는 방식도 가능하다.
- 팀 추가 목표에 따라 Windows 실행파일 및 macOS `.app` 패키지를 각각 만들고, 아이콘·더블클릭 실행을 확인한다.

## 14. 팀에서 추가로 결정해야 하는 사항

아래 내용은 PDF에서 정확한 수치나 구현 방법을 지정하지 않았으므로 팀 논의가 필요하다.

- 낙하 속도 증가 기준
  - 블럭 생성 개수 기준
  - 삭제된 줄 수 기준
  - 최소 낙하 간격을 둘지 여부
- 추가 점수 규칙
- Level 개념을 별도로 도입할지 여부
- 중복 키 설정을 허용할지 여부
- 설정 및 스코어보드 저장 형식
- UI 세부 구성
- 색맹 모드의 구체적인 표현 방식
- 텍스트 기반 UI와 Swing 사용 범위(필요 시 교수님께 확인)
- 다음 블럭 미리보기 개수와 블럭 무작위 선택 방식
- 지원할 macOS CPU 아키텍처와 OS별 배포 검증 범위
- 점수 동률·이름 입력·파일 손상 시 처리 방식
