# 팀원 의견을 기준으로 나눈 Req2 진행안

2026-10-22 기준. 이 문서는 팀원 의견과 요구사항을 구분한 **제안**이다.
아이템 선택·세부 규칙·담당자·기한은 아직 팀에서 확정하지 않았다.
게임 코드를 구현하거나 동작을 변경한 문서는 아니다.

## 1. 필수 기능과 선택할 내용을 먼저 구분한다

| 구분 | 반드시 충족할 내용 | 팀이 결정할 내용 |
|---|---|---|
| 배포·검증 | 아이콘이 있는 실행파일, 더블클릭 실행, 실행·주요 기능 검증 | 지원 OS/CPU, 실행파일을 Git에 넣을지 배포 파일로 전달할지 |
| 난이도 | EASY/NORMAL/HARD, I 블록 가중치·줄 삭제 가속 변경, 저장, 난이도 표시 | 추가 점수 규칙, 기존 생성 수 가속과 결합 방식 |
| 확률 테스트 | 실제 게임 생성 코드를 1,000회 이상 실행, 기대 분포와 ±5% 오차 비교 | 반복 횟수 확대, seed, 오차 비교 방식 명시 |
| 줄 삭제 애니메이션 | 삭제되는 줄을 알아볼 수 있는 표시 | 한 번 반짝이는 색·시간·표시 중 입력 정책 |
| 아이템 모드 공통 | 별도 시작 메뉴, 모드별 기록 구분, 10줄마다 아이템, 미리보기 반영, 서로 다른 문자 | 아이템 선택 확률, 효과 순서, 중첩·점수 정책 |
| 필수 아이템 | 줄 삭제 L + 너비 4칸 무게추 | 무게추의 구체적 모양·문자·회전·바닥 도착 후 처리 |
| 팀 아이템 | **직접 구상한 아이템 최소 3개 추가** | 팀원 후보 중 어떤 3개를 구현할지 |

따라서 “아이템 요구사항이 없음”이라는 부분은 수정해야 한다.
최소 구성은 **필수 2개 + 팀 아이템 3개 = 총 5개 이상**이다(Req2 7~10쪽).
자유로운 부분은 팀 아이템의 내용과 상세 화면 구성이다.

가중치 생성과 분포 테스트는 필수다. Roulette Wheel Selection은 Req2에서 사용할 수 있다고 제시한 방법이며,
이름 그대로의 알고리즘만 강제한 문구는 아니다. 팀 구현은 가중치 누적 구간으로 선택하는 방식으로 통일하는 것을 제안한다.
I 가중치는 EASY 12 / NORMAL 10 / HARD 8, 나머지는 각각 10이다.
“20% 증가”를 확률에 20%p를 더하는 것으로 구현하지 않는다.
±5%가 상대 오차인지 퍼센트포인트인지 비교 방식을 기록하고, 확인이 필요하면 수업 문의로 해소한다.
기존 #17의 보수적인 상대 오차 5% 검사는 제안이지 원문에서 명확히 정한 해석은 아니다.

무게추는 **세로 4줄 삭제가 아니라 가로 너비 4칸**이다.
처음에는 좌우 이동이 가능하고, 바닥이나 다른 블록에 처음 닿으면 좌우 이동이 금지된다.
아래 블록을 지우며 내려가야 하므로 일반 블록처럼 첫 충돌에서 즉시 고정하면 안 된다.
기본 규칙은 사용·파괴에 점수가 없고, 별도 점수는 팀이 정할 수 있다(Req2 9쪽).

## 2. 팀원 아이템 후보를 비교한다

구현 부담은 현재의 7종 블록·일반 충돌·점수 구조를 기준으로 한 상대적인 예상이다.

| 후보 | 효과 분류 | 예상 부담 | 먼저 정할 점 | 이번 범위 제안 |
|---|---|---|---|---|
| 폭탄 | 고정 시 주변 칸 삭제 | 낮음~중간 | 5×5 중심 칸, 가장자리, 자기 블록 포함 여부, 점수 0 | 채택 추천 |
| 황금 블록 | 고정 후 줄 삭제 시 점수 변경 | 중간 | 5배 적용 범위, 같은 줄의 황금 여러 개, 다른 아이템으로 파괴된 경우 | 채택 추천 |
| 1칸 블록 | 작은 모양으로 빈칸 채우기 | 낮음~중간 / 시간 무제한은 추가 부담 | 자동 낙하·하드드롭, 회전, 점수 | 일반 자동 낙하를 유지하는 안 추천 |
| 변신 블록 | 낙하 중 모양 변경 | 중간~높음 | 새 모양 충돌, 변환 순서, 입력 키·키 설정, 아이템 위치 | 후속 후보 |
| 중력 붕괴 | 고정된 칸을 아래로 이동 | 높음 | 범위, 칸/묶음 이동, 연쇄 줄 삭제, 점수·10줄 보상 | 후속 후보 |
| 모래·슬라임 | 칸이 아래·옆·대각선으로 퍼짐 | 높음 | 이동 우선순위, 처리 순서, 안정될 때까지 반복, 경계·연쇄 | 후속 후보 |

추천 조합은 **L / W / B / G / P**다. 문자도 확정 전 제안이다.
`L`은 요구사항에서 지정했고, 나머지는 서로 다른 문자를 사용한다.
모래·중력 붕괴는 보드 전체의 이동 규칙과 연쇄 처리를 크게 늘리므로 기본 아이템 흐름이 안정된 뒤 검토한다.
변신은 입력과 충돌 규칙을 함께 바꾸므로 첫 구현 범위에서는 뒤로 둔다.
1칸 블록의 시간 무제한은 일반 낙하 요구와의 관계, 게임 진행 정지·점수 악용 가능성을 따로 정해야 한다.
이번에는 자동 낙하와 기존 하드드롭을 유지하는 쪽을 제안한다.

이전 문서의 3×3 폭탄·세로 지우개·감속도 확정안은 아니었다.
이번 팀원 의견의 폭탄은 **5×5**이며, 이번 추천은 위 L/W/B/G/P 구성으로 갱신한다.

## 3. 추천 아이템의 최소 규칙을 문장으로 정한다

아래 규칙은 구현 담당자가 서로 다른 동작을 만들지 않기 위한 초안이다.
팀이 결정하면 이 표를 확정 명세와 평가팀용 설명으로 갱신한다.

| 아이템 | 발동·동작 초안 | 점수 초안 | 꼭 확인할 테스트 |
|---|---|---|---|
| L 줄 삭제 | 일반 블록의 무작위 한 칸에 L. 회전도 함께 적용. 고정된 실제 행을 삭제 | 기존 줄 삭제 방식. 꽉 찬 행과 겹쳐도 중복 가산 없음 | 부착 위치, 회전, 비어 있는 행, 일반 삭제와 중복 |
| W 무게추 | 너비 4칸. 첫 접촉 후 좌우 이동 금지, 아래 블록을 지우며 하강 | 낙하·파괴에 0점 제안 | 첫 접촉 전후 좌우 입력, 아래 장애물, 즉시 낙하, 바닥 |
| B 폭탄 | 무작위 표시 칸 B를 중심으로 고정 시 5×5 제거. 범위 안의 자기 칸도 포함, 보드 밖 무시 | 파괴한 칸에는 0점. 일반 낙하 점수 유지 제안 | 모서리·가장자리, 자기 칸, 다른 아이템 파괴, 범위 밖 보존 |
| G 황금 | 일반 블록의 한 칸에 G. 고정 후에도 남고 그 칸이 들어 있는 행을 삭제하면 발동 | 해당 삭제 이벤트의 기본 줄 삭제 보너스만 5배. 낙하 점수 제외, 중복해도 5배 제안 | 고정 후 표시 유지, 복수 행, 복수 G, 파일과 무관한 게임 상태 사본 |
| P 1칸 | 한 칸짜리 모양. 일반 자동 낙하·좌우·아래·하드드롭 사용, 회전은 모양 변화 없음 | 일반 낙하·줄 삭제 점수 | 벽·바닥, 마지막 빈칸 채우기, 미리보기, 하드드롭 |

G 점수 초안의 예: 두 줄 삭제 보너스가 300점이고 그중 G가 있는 행이 삭제되면 1,500점.
같은 삭제에 G가 여러 개 있어도 1,500점이며, 낙하 점수는 별도로 계산한다.
B/W가 G 칸만 파괴한 경우는 행 삭제가 아니므로 5배를 발동하지 않는 안을 제안한다.
이 계산은 팀원 표현의 모호한 부분을 구체화한 **새 제안**이며, 요구사항으로 확정된 5배 해석이 아니다.

팀에서 추가로 정해야 하는 내용:

- 10줄 보상은 누적값이 9→10·9→12·19→21일 때 모두 한 번 발생하도록 할지.
- 아이템으로 지운 행도 보상 누적에 넣을지, 여러 기준을 넘으면 보상을 어떻게 대기시킬지.
- 아이템이 미리보기에 표시된 뒤에는 실제 등장 시 종류·붙은 위치가 바뀌지 않도록 보장하는 방법.
- W의 회전, 바닥 도착 후 남는지/사라지는지, 위에 남은 칸에 별도 중력을 적용할지.
- 일반 줄 삭제와 아이템 효과, 황금 배수, 보상과 애니메이션 순서.
- 아이템으로 한 번에 5줄 이상 삭제할 때의 점수. 현재 점수 함수는 최대 4줄만 허용한다.

## 4. 코드를 나눌 때는 아이템 종류보다 공통 연결 부분을 먼저 정한다

아이템마다 엔진과 화면 여러 곳에 조건문을 추가하면 교수님이 지적한 확장성 문제가 반복된다.
먼저 아래 정보가 모듈 사이에 전달되게 하고, 그 뒤에 각 아이템을 연결한다.
이름은 예시이며 구현 API를 확정한 것은 아니다.

| 공통 정보·역할 | 필요한 이유 |
|---|---|
| 게임 시작 정보: 모드 + 난이도 | 게임 시작·다시 시작·저장·기록에서 같은 값을 사용 |
| 블록 정보: 칸 목록 + 칸별 아이템 | L/G 위치, W/P 모양을 엔진·보드·미리보기가 함께 표현 |
| 이동/접촉 규칙 | W가 일반 블록과 다른 충돌·좌우 이동·하드드롭 동작 사용 |
| 아이템 효과 처리 | B/L 등 새 효과를 엔진의 긴 조건문 없이 추가 |
| 줄 삭제 결과: 행 번호 + 삭제 전 칸 정보 + 원인 | G 점수, 중복 삭제 방지, 애니메이션, 10줄 보상에 같은 결과 사용 |
| 화면 상태: 현재/다음 블록 + 삭제 예정 행 | 미리보기와 실제 블록 일치, 삭제 전 표시 |

**삭제 결과에 아이템 정보가 남아야 한다.** 보드를 압축한 뒤 G가 있었는지 찾아서는 정보가 사라진다.
**블록의 칸 수를 4로 가정하지 않아야 한다.** W와 P를 기존 데이터로 표현할 수 있는지 확인한다.
**무게추를 고정 후 효과 하나로만 처리하지 않는다.** 접촉 이후에도 내려가는 이동 규칙이 필요하다.
애니메이션은 삭제할 행을 표시한 후 압축·다음 생성을 진행하며, Swing 이벤트 스레드에서 sleep하지 않는다.

## 5. 작업 순서와 담당 범위를 정한다

이 표는 기존 모듈을 기준으로 한 역할 제안이다. 메이님·진린투님 등 실제 이름과 기한은 팀 합의 후 이슈에 넣는다.
각 담당자가 자기 기능 테스트를 함께 작성한다.

| 역할 | 맡을 범위 | 먼저 받거나 전달할 정보 |
|---|---|---|
| 보드·블록 | 아이템 칸 정보, 회전, W/P 모양, 칸·행 삭제와 이동 | 블록 데이터와 삭제 결과 형식 |
| 엔진·규칙 | 가중치 생성·난이도 속도, 10줄 보상, L/W/B/G/P 처리 순서·점수 | 이동·접촉 API, 삭제 결과, 시작 설정 |
| 화면·입력 | 모드 메뉴, 아이템 문자·미리보기·색각 표시, 줄 삭제 반짝임 | 화면 상태와 삭제 예정 행 |
| 앱·저장·배포 | 난이도 저장, 모드별 시작·재시작·기록, 예전 파일 호환, 실행 패키지·검증 기록 | 게임 시작 정보, 점수 기록 형식 |

진행 순서:

1. **실행 기준 확보:** Windows PR #15와 macOS PR #20의 패키지를 각 OS에서 확인하고 소스 커밋·파일 확인값을 기록한다.
2. **짧은 설계 합의:** 추천 아이템 3개와 위 공통 데이터, 발동 순서, 점수 초안을 정한다. 이슈 #16에 결정 이유를 남긴다.
3. **공통 구조부터 작은 PR:** 아이템 없는 일반 모드가 그대로 동작하는 상태에서 블록 정보·삭제 결과·시작 설정을 연결한다.
4. **L 하나를 끝까지 연결:** 10줄 보상→미리보기→생성→회전→고정→행 삭제→점수까지 테스트한다.
5. **W를 연결해 확장성 확인:** 다른 이동·접촉 규칙을 기존 구조에 넣을 수 있는지 확인한다. P/B/G도 합의된 역할에 따라 연결한다.
6. **공통 기능 병행:** 구조/API가 정해지면 난이도·확률 테스트, 화면·애니메이션, 저장·기록을 각 담당이 진행한다.
7. **한 소스 기준으로 통합:** 기존 테스트와 새 테스트, 전체 커버리지, 실제 실행을 확인한 뒤 평가용 패키지를 다시 만든다.
8. **평가팀 자료 작성:** 확정 아이템 명세, 조작법·시연 순서, 설계 변경 이유와 요구사항별 테스트를 제공한다.

여러 아이템 담당자가 동시에 `GameEngine`, `Board`, 점수 코드 전체를 수정하는 방식은 피한다.
공통 부분 담당과 연결 API를 먼저 정하고, 새 효과 구현은 정해진 경계 안에서 진행한다.
브랜치·PR은 작업 단위로 만들고 본문에 연결 이슈·담당 범위·검증 결과를 적는다.

## 6. 배포와 각 OS의 수동 검증은 별도로 추적한다

| 항목 | 현재 확인 상태 | 다음 작업 |
|---|---|---|
| Windows | PR #15에 `build/windows-x64/Tetris/Tetris.exe`와 Java가 포함됨. 작성자가 검증 결과 기록 | 다른 팀원이 해당 패키지를 내려받아 독립 확인 |
| macOS | PR #20에서 `build/macos/Tetris.app` 생성. 로컬 실행과 CI 패키징 확인 | 다른 Mac에서 내려받은 패키지의 첫 실행·설정·점수 유지 확인 |
| 코드 커버리지 | 기존 main 기준 92.74%, 중간평가 전체 줄 50% 기준 충족 | Req2 변경 후 다시 측정하고 결과 기록 |

macOS의 `.app` 자체가 앱 폴더이므로 `build/macos/Tetris.app`도 OS별 경로를 나눈 구성이다.
현재 방식은 Windows가 실행파일을 Git에 직접 추가했고, macOS는 생성 코드와 Actions Artifact를 제공한다.
**실행 경로와 Git에 올릴 파일 범위는 별개의 결정**이다. 저장소에 패키지도 포함할지, 배포 파일로 통일할지는 #18에서 합의한다.
배포 방식이 정해지면 Windows와 macOS의 파일 구성·안내를 맞춘다.
macOS의 지원 CPU는 현재 arm64이며 Intel은 별도 검증이 필요하다.

각 OS에서 같은 점검표를 사용한다:

1. OS·CPU·소스 커밋·패키지 확인값과 확인자를 기록한다.
2. 압축 해제 후 실행파일을 더블클릭한다. 명령어나 추가 Java 설치가 필요한지 확인한다.
3. 게임 시작, 좌우·아래·회전·하드드롭, 키 반복 입력을 확인한다.
4. 일시정지·재개, 설정 진입과 복귀, 메뉴 복귀·다시 시작, 종료를 확인한다.
5. 창 크기 3종, 조작 키, 색각 모드·패턴을 확인한다.
6. 게임오버 후 이름 등록·순위·신규 기록 강조를 확인한다.
7. 종료 후 다시 실행해 설정·점수 기록이 유지되는지 확인한다.
8. Req2 통합 후 같은 항목에 난이도·아이템·모드별 기록을 추가해 다시 확인한다.

CI 성공은 다른 사람이 다운로드한 실행파일의 첫 실행을 확인한 것과 구분해서 기록한다.
수동 검증 기록에는 확인하지 않은 항목을 통과로 표시하지 않는다.
